# SiliconLoop

**在 ESP32-P4 上让 AI Agent 自主诊断硬件故障**

2026 首届 openvela AI 硬件开发者大赛 · 队伍 330 · 内核游牧者

---

## 一、解决什么问题

嵌入式开发中有一类故障，mock 测试永远发现不了：

```c
while (!fifo_has_space())
    usleep(1000);
fifo_put(g_produced++);
```

这段代码的逻辑是：等 FIFO 有空间后写入。如果消费者停止消费，
FIFO 填满，`fifo_has_space()` 永远返回 false，循环永不退出。

在 mock 环境里 `fifo_has_space()` 是一个桩函数，恒返回 true——
没有真实的 FIFO，没有真实的容量限制。测试全绿，代码看起来没问题。

只有在真机上，FIFO 真的有 64 字节，真的会满。

需要说清楚的是：正常情况下 FIFO 也会填满。生产者每 10 毫秒放一个
字节，消费者每 20 毫秒取一个，生产比消费快一倍。满了之后生产者
等待，消费者不断取走腾出空间，整个系统被拖慢到消费者的速度，但
一直在前进。

故障不是「FIFO 满了」，而是「满了之后再也不会空」——消费者停了，
生产者永远等不到空间。

这类故障的特点是：**在模拟环境中无法复现，在真机上又不崩溃、不
报错，只是"不动了"**。传统做法是工程师盯着串口日志手动分析。
SiliconLoop 的做法是让 AI Agent 在板上自主运行，周期性采集系统
状态，自动判断任务是否卡死。

## 二、怎么做的

### 主线一：Agent 心跳自诊断

AI Agent 运行在 ESP32-P4 上，每 120 秒被心跳服务自动唤醒，执行
一次七步诊断：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | `read_file` HEARTBEAT.md | 获取本轮任务描述 |
| 2 | `read_file` self-diagnostic.md | 加载诊断 Skill |
| 3 | `read_file` heartbeat.txt | 第一次采样 |
| 4 | `run_shell "ps"` | 进程列表 |
| 5 | `run_shell "free"` | 堆内存状态 |
| 6 | `read_file` heartbeat.txt | 第二次采样 |
| 7 | `write_file` report.md | 写出四段式报告 |

**核心判据是两次采样的差值。**

被监控的任务每生产 50 个数据就往 heartbeat.txt 写一个递增计数。
两次采样之间由步骤 4、5 自然拉开十余秒——Agent 的工具集里没有
sleep，用别的工作填满间隔是绕过这个限制的办法。

计数增加说明任务在前进，不变说明卡住了。

**这个判据是唯一无歧义的指标。** `ps` 在正常和故障状态下看到的
完全相同：buggy_app 的生产者和消费者始终是两个线程，状态都正常。
一个卡在死循环里空转的程序，在进程列表里和正常工作的程序长得
一模一样。

全程无人干预。Agent 自己读文件、执行命令、调用 LLM 分析、写报告。
报告落盘到 `/data/ai_agent/evidence/report.md`，四段式：观察到的
证据、假设、置信度、建议的下一步。

### 主线二：为 ESP32-P4 补上 ELF 动态加载

ESP32-P4 在 openvela 上此前无法执行编译期之外的程序。NuttX 的
`elf` 示例加载模块后，第一条指令就触发异常。

定位并修复两层根因（详见第四节）后，七个测试全部通过：errno、
hello、signal、struct、mutex、pthread、task，含模块内再次 exec。
每个测试结束后内存收支归零。

这是平台级的基础能力，不局限于本项目——任何需要在运行时加载
插件、模块、用户程序的应用都用得上。

## 三、关键数据

### 162 轮无人干预回归测试

修复定时任务缓存缺陷后，连续运行约 5.5 小时：

| 指标 | 数值 |
|---|---|
| 总轮数 | 162 |
| 成功 | 153（94.4%） |
| 其中完整执行七步 | 148（91.4%） |
| 失败 | 8（4.9%） |
| 缓存命中（空转） | **0** |
| 单轮耗时 | 15s ~ 208s，中位 109s |

**口径说明**：162 是心跳触发总数（`BEGIN`），153 是成功结束数（`END status=ok`），8 是失败数（`END status=fail`）。差的 1 轮是拷贝日志时仍在进行中。148 是其中完整走完七步（`iters=7 tools=7`）的轮次，差的 5 轮成功但步数不足，属正常波动。

![回归数据](evidence/2026-09-19/regression-clean.png)

三张图分别是：每轮耗时分布、单轮内请求体增长、跨轮首次请求大小。
第三张的水平线是修复缓存缺陷后的效果——修复前那三个灰色方块逐轮
上升，第三轮就失败了。

8 次失败原因完全一致：第 7 步（写报告）的请求体序列化 OOM。
`latency=0ms` 表明请求未发出，是构造阶段失败而非网络问题。此时
空闲总量仍有数十 KB，但已无足够大的连续块——是碎片而非耗尽。

### 与修复前的对比

| | 修复前 | 修复后 |
|---|---|---|
| 总轮数 | 114 | 162 |
| 真正执行诊断 | 53（46%） | 148（91%） |
| 缓存空转 | 57 | 0 |
| 按真实执行数计的失败率 | 7.5% | 5.1% |

修复前近半数轮次命中了 LLM 响应缓存：`llm_ms=0`、`tools=0`、
`status=ok`——日志看起来一切正常，任务却从未运行。

这个缺陷靠读日志发现不了，只有统计工具调用次数才暴露。修复方式
是 system 通道不再查询缓存：周期检查的意义就在于观察系统此刻的
状态，而那从来不可缓存。

### 正常与故障对照

| 状态 | 第一次采样 | 第二次采样 | Agent 判定 |
|---|---|---|---|
| 正常 | 800 | 1000（+200） | 任务存活，报告 healthy |
| 故障注入 | 50 | 50（无变化） | 任务停止前进 |

同一个 Skill、同一套七步流程，什么都没改，靠真实数据区分两种状态。

两份报告里的 `ps` 输出几乎相同——都是两个 buggy_app、都没有异常
状态。区别只在心跳那一行。

## 四、技术难点

### ELF 动态加载：两层异常，五个被排除的假设

加载 ELF 模块后触发异常：

```
riscv_exception: EXCEPTION: Instruction access fault.
MCAUSE: 00000001, EPC: 4ff72840, MTVAL: 4ff72840
```

MCAUSE=1 是 RISC-V 的「取指被拒绝」。在此之前每一步都成功了：
romfs 挂载、ELF 解析、段加载、符号绑定、数十次重定位写入全部
正常，任务也创建了。**同一块内存可写不可执行**——只有第一条
指令取不出来。

#### 沿途排除的五个假设

每一条都有依据，不是推测：

1. **需要数据/指令总线地址转换。** ESP32-C3 的移植里有
   `esp32c3_textheap.c`，把堆地址加一个偏移换成指令总线地址。
   查 P4 的 `soc.h`：`SOC_IRAM_LOW` 与 `SOC_DRAM_LOW` 同为
   `0x4ff00000`——统一地址空间，不需要转换。排除。

2. **MMU 映射缺少执行权限。** 查 `esp_start.c` 中的
   `mmu_hal_map_region` 调用，目标是 `MMU_TARGET_FLASH0`——
   这个 MMU 只映射外部 Flash，不涉及内部 SRAM。排除。

3. **入口地址计算错误。** REL 类型 ELF 的 `e_entry` 为 0，怀疑
   加载器算错了跳转目标。开启 `CONFIG_DEBUG_BINFMT` 后日志显示
   `entrypt` 与 `textalloc` 一致，而 `e_entry=0` 对可重定位目标
   文件属正常。排除。

4. **ISA 不匹配。** `readelf -A` 对比模块与内核：两者同为
   `rv32i2p1_m2p0_a2p1_c2p0_zicsr2p0_zifencei2p0`。排除。

5. **链接器松弛重定位处理有误。** 日志里满屏的 `RELAX` 记录引起
   怀疑。给测试模块加 `-mno-relax` 重新编译，`readelf -r` 确认
   `RISCV_RELAX` 条目从 3 个降为 0——仍然崩溃。移除该参数后表现
   完全相同。排除。

#### 第一层定位：板上读 PMP 寄存器

软件层面排除干净后转向硬件权限。在被测程序里加一个子命令，用
内联汇编读取 PMP 配置寄存器并打印：

```
PMP05 cfg=8d R1 W0 X1 TOR L1 top=4ff49500
PMP06 cfg=8b R1 W1 X0 TOR L1 top=4ffc0000
```

PMP06 是 **RW 无 X**，失败的入口地址 `0x4ff72840` 正落在它的范围
内。堆位于这个区间，模块代码加载到堆上，所以可写不可执行。

两条规则都带 L（lock）位——机器模式同样受限，且复位前无法修改。

根源是 esp-hal 的 `sdkconfig.h` 硬编码了
`CONFIG_ESP_SYSTEM_MEMPROT=1`。**该项不出现在 NuttX 的 `.config`
中，源码检索容易漏过**——我们最初 grep 不到它，因此误以为 PMP
未被配置。它使 `cpu_region_protect.c` 以 `_iram_text_end` 为界把
SRAM 切成 RX 与 RW 两段。

修复：将 PMP06 及其非缓存别名（entry 9）的权限从 RW 改为 RWX。

#### 第二层定位：内存 dump 与主机 objdump 逐字节比对

修复 PMP 后异常变为：

```
riscv_exception: EXCEPTION: Illegal instruction.
MCAUSE: 00000002, EPC: 4ff72980, MTVAL: 00000000
```

错误码从 1 变成 2 本身就是进展：CPU 现在**被允许**取指了，只是
读到的内容不是有效指令。

在跳转前打印 `textalloc` 处的前 16 字节：

```
板上:  41 11 05 45 06 c6 26 c2 22 c4 97 00 0a f0 e7 80
主机:  41 11 05 45 06 c6 26 c2 22 c4 97 00 00 00 e7 80
```

只有第 13、14 字节不同，而那正是 `auipc` 的重定位结果——**内存
内容完全正确**。

问题只可能在取指路径。模块代码是经数据通路写入的（每次重定位
都是一条 store），取指走另一条通路，而 P4 的内部内存经 L1 缓存
访问且为写回模式（`SOC_CACHE_INTERNAL_MEM_VIA_L1CACHE=1`），
代码仍留在数据缓存中，取指侧读到旧字节。

**实测 `fence.i` 单独不足。** 它排序的是访存与取指，不负责把
写回缓存刷出——只加 `fence.i` 仍然复现。

最终修复：重定位完成后对代码段写回并失效。

```c
cache_hal_writeback_addr(textalloc, textsize);
cache_hal_invalidate_addr(textalloc, textsize);
```

#### 小结

| 层 | 异常 | 定位手段 | 修复 |
|---|---|---|---|
| 一 | MCAUSE=1 取指被拒 | 板上读 PMP 寄存器 | 堆区 RW → RWX |
| 二 | MCAUSE=2 指令无效 | 内存 dump 与 objdump 逐字节比对 | 写回 + 失效缓存 |

两处改动加起来不到二十行，但定位花了五个多小时。

| [packages_ai_agent#39](https://github.com/open-vela/packages_ai_agent/pull/39) | 上一条的修复 PR，尚未合并 | 0009 |

另有若干真机上发现、尚未提交上游的缺陷，详见 `patches/README.md`。
其中几条不限于本项目——任何无 RTC、未开 RPMSG、或在资源受限设备
上部署 ai_agent 的项目都会遇到：

- **TLS 发送超时缺失**：`tls_ctx_free()` 首先调用
  `mbedtls_ssl_close_notify()` 向已失效的 socket 写数据，而
  `SO_SNDTIMEO` 仅在 `CONFIG_AI_AGENT_NET_RPMSG` 下设置。没有
  发送超时的阻塞写永久等待，agent 主循环随之完全无响应。

- **连接池复用被静默关闭的连接**：复用前的 10ms 探测读只能识别
  对端发送 `close_notify` 的情况。服务器回收空闲连接时通常不发
  通知，检查因此放行，随后的请求在 TCP 重传中停滞约 100 秒。
  实测三次为 93.8 / 112.8 / 125 秒。

- **定时任务被响应缓存永久短路**：缓存键只有提示词哈希。定时
  任务每次发相同提示词，一旦某轮回复进入缓存，之后每次触发都
  直接返回它，任务从不运行，而日志仍显示 `status=ok`。

- **HEARTBEAT.md 与 cron.json 路径错位**：创建在
  `AGENT_CONFIG_DIR`，读取在上一级。文件从不存在于读取方查找的
  位置，两个服务从未工作过。

- **本地工具捷径截断多步推理**：读完 Skill 文件后直接把内容当
  最终答复返回，后续步骤不再执行。上游已为 skills 目录打过同类
  补丁，HEARTBEAT.md 与「Skill 执行期间」两种情形尚未覆盖。

## 六、工程取舍与局限

### Agent 只诊断不修复

Agent 的工具集里只有只读命令，没有杀进程、改配置、重启的能力。
**这是刻意的限制。**

原因来自一次真实的误判：第一版 Skill 让 Agent 看进程列表判断
系统状态，它把 buggy_app 的两个正常线程（生产者 + 消费者）报成
了「重复启动 bug」，还建议「终止一个实例观察是否自动重启」。

如果它当时有修复权限，就会杀掉正常工作的程序。

当前策略是：Agent 负责采集、分析、写报告，由人决定下一步。自动
修复是下一步，前提是判据足够可靠。

### PMP 权限的牺牲

将堆区从 RW 改为 RWX，牺牲了数据区不可执行的防护——堆上的数据
理论上可以被当作代码执行。

正规方案是实现 `up_textheap_memalign()`，从内存中划出一块专用的
可执行区域，只对那块设 RWX。该移植尚未提供这一支持，实现它需要
改动链接脚本与内存布局。

我们也尝试过直接关闭 `CONFIG_ESP_SYSTEM_MEMPROT`（让整段 SRAM
变成 RWX），结果板子无法启动——该开关还牵连启动路径的其他分支。
只改一条 PMP 规则是风险更小的选择。

### 堆碎片化

404KB 堆在长时间运行后会碎片化。实测连续跑一百多轮诊断后，空闲
内存降到 34KB，TLS 握手因无法分配足够的连续内存而失败
（`ssl_setup ret=0x7f00`），`net_test` 也一并失败。

重启后恢复正常（空闲约 115KB）。当前的缓解方式就是定期重启。
更根本的方案需要从内存分配策略或 Agent 的内存使用模式入手。

### 8 次失败的根因

162 轮中 8 次失败，全部发生在第 7 步——写报告时的请求体是全流程
最大的一次（约 12.5KB），`cJSON` 序列化需要一块相应大小的连续
内存。此时空闲总量仍有数十 KB，但已无足够大的连续块。

这是 404KB 堆的固有限制。减少报告内容或分段序列化可以缓解，但
会增加复杂度。

### AI Coding 日志的缺口

本项目绝大部分开发使用网页版 Claude 完成。按大赛手册，网页版不在
官方支持的四种工具内，无法自动采集对话日志。`logs/` 目录只覆盖
收尾阶段。

排查过程本身留在了两处：`patches/README.md` 逐个补丁记录了现象、
根因、解法与局限；`docs/evidence/` 保留了每个结论对应的原始日志，
包括那些被排除的假设。

完整代码与补丁在参赛仓库 `contest2026_330_neiheyoumuzhe`。

**快速验证**（不需要 LLM 密钥）：按 README 的运行方式完成编译
烧录后，在板上执行 `elf`，预期七个测试全部通过。这条路径验证的
是 ELF 动态加载能力。

**完整演示**：配置 `agent_secrets.h` 中的 LLM 地址与密钥，重新
编译烧录后运行 `buggy_app &` 与 `ai_agent`，等待心跳自动触发。

**技术细节**：`docs/technical-deep-dive.md`。

**原始数据**：`docs/evidence/`，文档中的每个数字都能在这里找到
出处。
