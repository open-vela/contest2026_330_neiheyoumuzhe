# 技术深度文档：两个核心问题的定位过程

本文档记录 SiliconLoop 项目中两个技术成果的排查过程。重点不是"修了什么"，而是"怎么查出来的"。

---

## 一、ELF 动态加载：两层异常，五个被排除的假设

### 背景

ESP32-P4 在 openvela 上不支持 ELF 动态加载。NuttX 的 `elf` 示例加载模块后，第一条指令就触发异常。我们需要搞清楚：是加载过程出了错，还是执行环境不允许？

### 第一个现象：取指被拒

```
riscv_exception: EXCEPTION: Instruction access fault.
MCAUSE: 00000001, EPC: 4ff72840, MTVAL: 4ff72840
```

MCAUSE=1 是 RISC-V 的"指令访问错误"——CPU 不允许从这个地址取指令。

此时加载过程的每一步都成功了：romfs 挂载、ELF 解析、段加载、符号绑定、数十次重定位写入全部正常，任务也创建了。只有第一条指令取不出来。

#### 沿途排除的假设

**假设 1：地址转换错误**

ELF 模块的段地址是链接时确定的，加载到内存后需要确认实际地址是否正确。检查方法：在加载完成后打印 `textalloc` 的值（即代码段实际加载地址），与 ELF 头中的 `e_entry` 比较。结果一致，地址转换没有问题。

**假设 2：MMU 映射问题**

ESP32-P4 有 MMU，但 openvela 在该平台上使用 Simple Boot，不经过二级引导程序，MMU 由 ROM 初始化后保持原状。检查方法：确认 `CONFIG_ESP_SYSTEM_MEMPROT` 的状态。发现 esp-hal 的 `sdkconfig.h` 硬编码了 `CONFIG_ESP_SYSTEM_MEMPROT=1`，而 NuttX 的 `.config` 中查不到此项——它不是通过 menuconfig 设置的，而是 esp-hal 内部的默认值。

**假设 3：入口地址计算错误**

ELF 的 `e_entry` 字段指向模块的入口点。需要确认加载后跳转的地址是否就是 `e_entry`。检查方法：在 `exec` 跳转前打印目标地址，与 `readelf -h` 输出的入口地址比较。结果一致。

#### 定位：板上 dump PMP 寄存器

排除了软件层面的问题后，转向硬件权限。RISC-V 用 PMP（Physical Memory Protection）控制内存访问权限。在板上用内联汇编读取 PMP 配置寄存器和地址寄存器：

```
PMP05 cfg=8d R1 W0 X1 TOR L1 top=4ff49500
PMP06 cfg=8b R1 W1 X0 TOR L1 top=4ffc0000
```

解读：
- PMP05：cfg=0x8d = R(1) W(0) X(1) TOR(01) L(1)，范围到 0x4ff49500，**可执行**
- PMP06：cfg=0x8b = R(1) W(1) X(0) TOR(01) L(1)，范围到 0x4ffc0000，**不可执行**

失败的入口地址 0x4ff72840 落在 PMP06 范围内（0x4ff49500 ~ 0x4ffc0000）。堆位于这个区间，ELF 代码被加载到堆上，所以可写但不可执行。

两条规则都带 L（lock）位，机器模式同样受限，复位前无法修改。

#### 修复

将 PMP06（和对应的非缓存别名 PMP09）的权限从 RW 改为 RWX。

#### 验证

应用补丁后，异常码从 1 变成 2——权限问题解决了，但暴露了第二层问题。

---

### 第二个现象：非法指令

```
riscv_exception: EXCEPTION: Illegal instruction.
MCAUSE: 00000002, EPC: 4ff72980, MTVAL: 00000000
```

MCAUSE=2 是"非法指令"——CPU 从这个地址读到了它不认识的指令。注意 MTVAL=00000000，说明取到的指令全是零。

#### 沿途排除的假设

**假设 4：ISA 不匹配**

ELF 模块是用 riscv32 编译的，ESP32-P4 也是 riscv32。但需要确认模块的指令集扩展（如 M、A、F、C）是否被板上 CPU 支持。检查方法：`readelf -A` 查看模块的架构标志，与 ESP32-P4 的 spec 比较。结果一致，都是 RV32IMC。

**假设 5：链接器松弛（linker relaxation）副作用**

RISC-V 链接器可能会做松弛优化，把某些指令序列替换为更短的形式。如果松弛过程中修改了指令但没有正确处理重定位，可能导致指令损坏。检查方法：对比模块在主机上 `objdump -d` 的反汇编与板上内存的实际内容。

#### 定位：板上 dump 内存 vs 主机 objdump

在跳转前，用 `md` 命令打印 `textalloc` 处的前 16 字节：

```
TEXT at 4ff72980: 41 11 05 45 ...
```

在主机上对同一份 ELF 做 `objdump -d`，找到对应地址的指令，逐字节比对——**完全一致**，包括正确的 `auipc` 重定位结果。

这证明了：内存中的内容是正确的，CPU 取到的却是全零。问题不在加载，而在取指路径。

#### 关键洞察：d-cache 与 i-cache 不一致

模块代码是经数据通路写入的——每一次重定位都是一条普通 `store` 指令。取指走另一条通路。

ESP32-P4 的内部内存经 L1 缓存访问（`SOC_CACHE_INTERNAL_MEM_VIA_L1CACHE=1`），且为写回模式。重定位后的代码仍然留在数据缓存中，没有写回到内存。取指侧从内存读到的是旧字节（全零或之前的值）。

#### 实测：fence.i 单独不足

RISC-V 有 `fence.i` 指令，用于同步指令流。最初尝试只加 `fence.i`，但实测仍然复现同样的异常。

原因：`fence.i` 排序的是访存与取指的顺序，但不负责把写回缓存刷出。数据还在 d-cache 里，`fence.i` 只是告诉 CPU"在继续取指之前，先完成前面的访存"——但访存写到的是 d-cache，不是内存。

#### 修复

重定位完成后，对代码段执行缓存写回 + 失效：

```c
cache_hal_writeback_addr(textalloc, textsize);
cache_hal_invalidate_addr(textalloc, textsize);
```

先写回（把 d-cache 中的脏数据刷到内存），再失效（让 i-cache 丢弃旧的缓存行，下次取指从内存重新加载）。

#### 验证

`elf` 示例七个测试全部通过：errno、hello、signal、struct、mutex、pthread、task，含模块内再次 `exec`。每个测试结束后内存收支归零。

---

### 小结

| 层 | 异常码 | 现象 | 定位手段 | 根因 |
|---|---|---|---|---|
| 第一层 | MCAUSE=1 取指被拒 | Instruction access fault | 板上 dump PMP 寄存器 | 堆区 PMP 权限无 X |
| 第二层 | MCAUSE=2 非法指令 | Illegal instruction, MTVAL=0 | 板上内存 dump vs objdump | d-cache 与 i-cache 不一致 |

五个假设的排除顺序：地址转换 → MMU → 入口地址 → ISA 匹配 → 链接器松弛 → 最终定位到 PMP 权限和缓存一致性。

## 二、定时任务被缓存永久短路：看起来正常，实际上从未运行

### 现象

L3 心跳自诊断服务配置为每 120 秒自动唤醒。日志显示每一轮都正常完成：

```
[agent] status=ok iters=7 tools=7
```

但仔细看 LLM 耗时和工具调用数：

```
[llm] llm_ms=0 tools=0
```

`llm_ms=0` 表示没有向 LLM 发送请求，`tools=0` 表示没有执行任何工具调用。日志显示 `status=ok`，但任务实际上从未运行。

### 排查：114 轮数据的统计分析

采集了连续 114 轮心跳的完整日志，编写 `tools/parse_regression.py` 逐轮提取状态、耗时、工具调用数、请求体大小。统计发现：

| 指标 | 数值 |
|---|---|
| 总轮数 | 114 |
| 真正执行诊断 | 53（46%） |
| 缓存空转 | 57（50%） |
| 按真实执行数计的失败率 | 7.5% |

114 轮里有 57 轮命中了缓存，`llm_ms=0`、`tools=0`，任务从未触达网络或执行任何诊断步骤。

### 根因：相同提示词 → 缓存命中 → 永久短路

定时任务每次发送的提示词完全相同（"读取 HEARTBEAT.md，执行自诊断 Skill"）。Agent 框架对 LLM 响应做了缓存，缓存键是提示词的哈希。

流程：
1. 第 N 轮正常执行，LLM 返回诊断报告，结果进入缓存
2. 第 N+1 轮触发，提示词相同，哈希命中缓存
3. 直接返回第 N 轮的缓存结果，不发送请求，不执行工具
4. 日志记录 `status=ok`（因为"成功返回了结果"）
5. 从此每一轮都命中同一个缓存项，任务永远不再运行

这是一个**正反馈故障**：一旦有一轮的回复进入缓存，之后所有轮次都被永久短路。而且从日志上看不出任何异常——`status=ok` 是真的，只是"成功返回"的是一个过时的缓存结果。

### 为什么这是危险的

定时任务的意义是**周期性观察系统当前状态**。心跳读数、进程列表、内存使用——这些都是时变数据。缓存一个过时的诊断报告，等于永远返回第一次检查的结果，无论系统实际状态如何变化。

如果设备在这期间发生故障，Agent 会继续报告"healthy"，因为缓存里的结论是上一次的。

### 修复

system 通道（定时任务使用的通道）不再查询缓存。周期检查的意义就在于观察系统此刻的状态，而那从来不可缓存。

### 验证：修复后的 162 轮回归

修复后重新采集了 162 轮数据（约 5.5 小时，无人干预）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 总轮数 | 114 | 162 |
| 真正执行诊断 | 53（46%） | 148（91%） |
| 缓存空转 | 57 | **0** |
| 按真实执行数计的失败率 | 7.5% | 5.1% |

修复后零缓存命中，148 轮完整执行七步诊断流程。

失败绝对数从 4 升到 8，但分母从 53 变成 156——修复前近半数轮次根本没有执行，自然不会失败。修复后的 8 次失败原因完全一致：第 7 步（写报告）的请求体序列化 OOM，是 404KB 堆上的内存碎片问题，与缓存无关。

### 小结

这个缺陷的特点是**隐蔽性**：日志看起来一切正常，`status=ok` 如实反映了"返回了结果"，但没有人检查这个结果是不是本轮新产生的。统计分析（对比 `llm_ms` 是否为零）是唯一的发现手段。
