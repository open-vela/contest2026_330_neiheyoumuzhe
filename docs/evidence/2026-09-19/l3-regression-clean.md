# L3 心跳定时自诊断 · 修复缓存缺陷后的回归数据

**日期**：2026-09-19
**运行时长**：约 5.5 小时，无人干预
**板子**：ESP32-P4，404,336 字节堆
**触发方式**：heartbeat 服务每 120 秒自动唤醒
**原始日志**：`l3-heartbeat-clean-162rounds.log`

## 结果

| 指标 | 数值 |
|---|---|
| 总轮数 | 162 |
| 成功 | 153（94.4%） |
| 其中完整执行七步 | 148（91.4%） |
| 失败 | 8（4.9%） |
| **缓存命中（空转）** | **0** |
| 单轮耗时 | 15s ~ 208s，中位 109s |

**口径说明**

三个数字的口径不同，不能直接相加：

- **162** 是日志中 `BEGIN` 的总数，即心跳触发次数
- **153** 是 `END status=ok` 的数量
- **8** 是 `END status=fail` 的数量
- 差的 **1 轮**是拷贝日志时仍在进行中的那一轮，有 `BEGIN` 无 `END`

148 与 153 的区别：153 是成功结束的轮次，148 是其中
`iters=7 tools=7`、完整走完七步的轮次。差的 5 轮成功但步数
不足——模型少调了一个工具就给出了结论，属于正常波动。

「真正执行诊断」的 156 = 148 完整执行 + 8 失败，即实际调用了
工具的轮次。

## 与修复前的对比

09-18 采集的 114 轮数据里，只有 53 轮真正执行了诊断，其余命中了
LLM 响应缓存：`llm_ms=0`、`tools=0`、`status=ok`——日志看起来一切
正常，任务却从未运行。

定时任务每次发送相同的提示词。一旦某一轮的回复进入缓存，之后每次
触发都直接返回它。修复方式是 system 通道不再查询缓存：周期检查的
意义就在于观察系统此刻的状态，而那从来不可缓存。

| | 修复前 | 修复后 |
|---|---|---|
| 总轮数 | 114 | 162 |
| 真正执行诊断 | 53（46%） | 148（91%） |
| 缓存空转 | 57 | 0 |
| 按真实执行数计的失败率 | 7.5% | 5.1% |

失败绝对数从 4 升到 8，但分母从 53 变成 156——修复前近半数轮次根本
没有执行，自然不会失败。

图三中少数点略高于基线，是提示词长度的正常波动（system prompt 会随
`/data` 下文件的大小微调，幅度在数十字节），与修复前那种每轮递增
260 字节、第三轮即失败的模式没有关系。

## 失败分析

八次失败原因与位置完全一致：
[agent] Skill in progress — no shortcut
[llm] OOM: failed to serialize request body
[trace] iter=6 tool=(none) latency=0ms llm=fail


`latency=0ms` 表明请求未发出，失败发生在构造阶段而非网络传输。
第 7 步（写报告）的请求体是全流程最大的一次，约 12.5KB，需要一块
相应大小的连续内存供 cJSON 序列化。404KB 堆上此时空闲总量仍有数十
KB，但已无足够大的连续块——是碎片而非耗尽。

这与 09-18 那批数据的结论一致，样本扩大后依然成立。

## 每轮执行的七步

1. `read_file` HEARTBEAT.md — 取得本轮任务
2. `read_file` self-diagnostic.md — 载入诊断 Skill
3. `read_file` evidence/heartbeat.txt — 第一次采样
4. `run_shell "ps"` — 任务列表
5. `run_shell "free"` — 堆状态
6. `read_file` evidence/heartbeat.txt — 第二次采样
7. `write_file` evidence/report.md — 四段式报告落盘

两次采样之间由步骤 4、5 自然拉开十余秒，不依赖 Agent 主动等待。

## 判据有效性

同一 Skill、同一流程，在两种状态下给出正确且不同的结论：

| 状态 | 心跳读数 | Agent 判定 |
|---|---|---|
| 正常 | 10900 → 10950 | alive，报告 healthy |
| 故障注入 | 50 → 50 | stall，报告任务停止前进 |

表中读数取自 09-18 的一轮实测；09-19 演示录制时的实测值为
800 → 1000 与 50 → 50，两者结论一致。

心跳增量是唯一无歧义的判据。`ps` 的任务数在两种状态下相同
（buggy_app 的生产者与消费者始终是两个线程），无法据此区分。
